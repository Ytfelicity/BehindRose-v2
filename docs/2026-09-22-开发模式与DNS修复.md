# 开发模式与 DNS 检测修复

本次按开发阶段要求只修改源码、构建 Debug 并运行验证，没有生成或更新发布 ZIP、安装包及发布 EXE。旧压缩包不包含本次修改。

## 开发入口

- `启动开发模式.cmd`：完整桌面功能，Debug 源码运行，检测页从源文件加载并监听修改。
- `启动检测页面.cmd`：本地检测页 `http://127.0.0.1:4317/`，HTML、CSS、JavaScript 保存后自动刷新。
- C# 支持的修改交由 dotnet watch 热更新；WPF XAML 未更新时可在控制台 Ctrl+R 重启。
- 开发模式使用独立单实例标记和 WebView2 用户数据目录，可与历史发布版区分。

## 复现与根因

真实浏览器检测中，IP 与 WebRTC 能取得结果，DNS 报“服务响应格式不匹配”。网络记录显示已申请会话、已查询结果，但没有发出域名探针。

根因是探针使用 `mode: 'no-cors'`，通用请求函数却统一指定 `redirect: 'error'`。跨来源 no-cors 请求要求 redirect 为 follow，否则在网络请求前即返回错误。[Fetch 标准](https://fetch.spec.whatwg.org/#main-fetch)

服务在未记录到解析器时返回 `{"error":"No DNS servers found. Try again..."}`。旧代码只接受数组，因而把服务错误误报成格式不匹配。

## 修改

- 域名探针使用 no-cors/follow；需要读取结果的 API 仍使用 cors/error。
- 保留固定 CSP 网络目标白名单、无凭据请求和超时取消。不忽略证书错误，也不关闭浏览器安全校验。
- 显式识别 DNS 服务的错误响应，“尚未记录到解析器”不再被当作格式错误。
- 检测报告区分桌面 WebView2 和本地开发页面的浏览器环境。

## 验证结果

- Debug 编译零警告、零错误。
- 桌面开发模式中的内存修复/恢复与本地 WebView2 页面加载检查通过。
- 源码监听及浏览器自动刷新验证通过，修改源文件后实际页面自动重载。
- 21 项 JavaScript 请求策略、地址校验与服务响应断言通过。
- 修复前网络记录缺少探针；修复后出现 8 个探针请求，DNS 结果查询实际返回解析器列表。
- 同时观察到 DNS 服务间歇性超时。该情况仍显示无法确认，不转换成“安全”或“无泄漏”。

本次真实外网复测来自本地开发页面；不将这次结果宣称为所有外部浏览器或全部系统流量的验证。未改动用户的 Clash、浏览器策略或系统网络设置。
