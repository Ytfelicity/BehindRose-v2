# 修复原来的网络连通性检测

用户明确要求修原检测、移除额外诊断、不改代理配置。本次移除了上一轮新增的 curl 分段诊断 UI、API、WebView 桥和 Windows 运行器；只保留原“检测本组”与网站表格。代理质量体检、VPS 体检等原有独立功能没有在本次扩展。

## 调整

- 同组站点可并行推进，上限十五站；移除连续模式三站队列造成的整组拖延。同一站点的请求严格顺序执行，不重叠。
- 默认七站，每站计划三次，显示最低成功值。采样方式直接写在下拉框，不暗中预热、不丢弃首测。单次模式和最多十次模式仍可选。
- 快速和单次模式的整组预算为五秒，十次模式为八秒；单次请求仍使用上游 3600 ms 超时。整组时限到达时取消活跃请求，停止排队任务，不等待慢站无限拖延。
- 原表显示成功次数 / 实际完成次数。“本次采样明细”保留每次结果、时间、首测、最低值及计划次数。部分采样到时限显示“采样未完成”。尚未启动的请求保留未检测，不能计作失败样本或零延迟。
- 明细和复制报告把“整组时限停止”与单请求完整超时区分；单站重测、切换分组后，汇总按当前可见行的真实样本重新计算，不混用上一组或最后重测一行的计数。
- 浏览器 GET 使用上游相同地址、no-cors、no-store、performance.now 计时；现有省略凭据和 Referer 的策略保留。不减去固定建连时间，不调整倍率，不用 HTTP 403 推断服务权限。

三次最低值和十次最低值的采样数量不同，不能声称两者具有完全相同的统计分布；单次模式也不应直接与多次最低值比较。同一网络不同时间仍可能有真实波动。本次调整解决排队、采样口径和等待上限，不能通过选择性丢弃失败制造所有站点正常的结论。

## 验证

调度回归覆盖：十五站同时推进、每站三次真实请求、同站无重叠、首测与最低值分别保留、失败不变零、整组超时停止活跃请求、快速站完成不受慢站阻挡、未启动站点没有虚假样本，以及取消后不会追加请求。

类型检查、采样调度回归、前端构建、桌面和开发 Host 构建通过，后端测试 49/49 通过。原生及 HTTP API 回归通过，并明确拒绝已移除的 website-timing 三个操作。本轮真实 UI 通过 CUA 操作原工作台按钮；没有运行另外的 Playwright UI 测试脚本。

Chrome 实测记录保存在忽略目录 `artifacts/connectivity-parity/`：

- `original-repaired-chrome-success.json`：默认七站完成 21/21，最低值依次为 Google 250、YouTube 248、GitHub 265、Cloudflare 286、Claude 272、ChatGPT 285、WeChat 17 ms。
- `original-single-comparison.json`：原检测单次七站均响应，页面数字与浏览器 Network 到响应的时间一致。GitHub 为 1427 ms，Network 记录约 1159 ms 在建连阶段；其余国际站约 258–303 ms。相邻时间同一 Chrome 的 IPCheck.ing 单次七站均到 3600 ms 被取消。这一对照不能声称两站每次都快或测值相同。
- `original-ai-quick.json`：AI 十五站实测 5.0 秒结束，完成 41/45 次请求，10 站响应、5 站失败或未完成。Midjourney 有浏览器 `ERR_BLOCKED_BY_RESPONSE.NotSameOrigin`；未响应站点保留未知，未伪造成零延迟或正常。
- 较早的 `original-repaired-chrome.json` 保留了原表七站全超时且未捕获 Network 事件的一轮；该轮原因未确定。之后重新启用 Network 追踪的两种模式拿到了真实请求和相符计时，没有通过修改代理或隐藏失败消除该记录。
- 重启项目开发服务并加载最终资源后，原工作台内嵌浏览器七站完成 21/21 次采样，实际用时 2.5 秒。原始结果见 `final-original-iab.json`，原界面截图见 `final-original-connectivity.png`。

这些记录支持并发调度、等待上限和原表计时的验证，不能把某次成功当作所有浏览器或每次网络状态的保证。

整个过程没有修改系统代理、TUN、DNS、路由、节点或浏览器代理配置。
