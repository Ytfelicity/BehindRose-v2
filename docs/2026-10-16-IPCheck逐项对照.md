# IPCheck.ing 与本地检测逐项对照

2026-10-16，在同一个 Chrome 工作配置中对照线上 IPCheck.ing、本地完整工作台和本地内部检测文档。没有修改代理、节点、路由、DNS、TUN、浏览器代理或 SSH 配置。

## 结论与边界

这次没有把“整组变快”当作“数值已与官网等价”的证据。实际下载并静态分析官网加载的检测代码，同时记录浏览器 Network 事件与两页显示值。

确认了三项影响比较的条件：

1. 旧本地默认 AI 组有 15 个目标，本次官网“我的”列表有 7 个目标。
2. 单次结果与连续采样最低值是两种统计口径。官网支持两种；本次 Chrome 会话实际只发送七个单次请求，不能笼统认定官网总在测十次。
3. 新建 TLS 连接与复用已建立连接，实际耗时会明显不同。本地一次 ChatGPT 请求总耗时约 1037 ms，其中 SSL 阶段约 770 ms，发出请求后等待首响应约 262 ms；官网另一次复用连接的同目标请求约 269 ms。本地后续复用连接的实测为 272 ms。

最后一项是从 Chrome 的实际分段计时读取，未从高低数值猜测。连接建立与 Waiting/TTFB 的定义参见 [Chrome Network 计时说明](https://developer.chrome.com/docs/devtools/network/reference/#timing-explanation)。不能把这三个独立采样当作同一时刻的固定延迟保证。

未发现本组样本有固定倍率的计时错误：本地页面七项显示值与对应 Chrome 网络事件耗时相差 0–1 ms。实际网络和网站响应仍会波动；官网对照过程中也出现过部分目标超时。本地最初七站全超时的具体网络阻塞原因没有被唯一定位，随后复测恢复；该失败保留，不能用成功复测删除它或推断所有路径正常。

同一浏览器也不保证两页共享已建立的连接。Chromium 的 [NetworkAnonymizationKey](https://chromium.googlesource.com/chromium/src/+/HEAD/net/base/network_anonymization_key.h) 包含顶层站点，[连接池分组代码](https://chromium.googlesource.com/chromium/src/+/HEAD/net/socket/client_socket_pool.cc) 在开启分区时使用该 key。由此可推断，官网已建立的连接不应被当成本地页必然可复用的连接；这只是比较条件的限制，不能据此认定本次所有超时都由连接分区导致。

下载来自 Chrome Network 响应正文，仅作静态解析，没有执行下载的脚本。SHA-256：`B9815ACA6DE36C10C75B3DB34FED1CDC9E82A66DD9F10F117F52D06AB2911CC9`。

| 项目 | 官网实际实现 | 本地实现 |
|---|---|---|
| 请求 | 浏览器 GET | 浏览器 GET |
| 模式 / 缓存 | no-cors / no-store | no-cors / no-store |
| 单次时限 | 3600 ms | 3600 ms |
| 单次计时 | fetch 前后的 performance.now 差 | 相同 |
| 快速组调度 | 每个目标间隔 50 ms 发起 | 相同，七站时无需分批 |
| 成功语义 | fetch 取得响应，状态码不作为服务权限验证 | 相同，跨域响应状态对网页不可见 |
| 七站地址 | Google、YouTube、GitHub、Cloudflare、Claude、ChatGPT 的 favicon，加微信固定图标地址 | 全部逐字一致 |
| Referrer | 请求携带官网 origin | 本地主动省略，保留隐私策略 |
| Cookie / 认证 | fetch 默认 same-origin；本次目标均跨域 | 显式 omit；本次七站请求未携带 Cookie 或认证 |
| 连续采样调度 | 上游有按 500 ms 间隔启动后续轮次的实现 | 本地最多三站、同站不重叠，队尾继续采样；没有声称连续调度逐字等同 |

参考上游源码与许可保留在 `vendor/MyIP/`。检测函数相同不代表所有宿主参数、用户偏好和浏览器连接状态都相同。

## 一组立即交替采样的结果

同一 Chrome、相同七个目标、单次模式，先官网后本地；没有同时发起两页检测。

| 目标 | 官网显示 ms | 本地显示 ms | 本地 Network ms |
|---|---:|---:|---:|
| Google | 253 | 258 | 258 |
| YouTube | 596 | 268 | 268 |
| GitHub | 1290 | 2040 | 2040 |
| Cloudflare | 445 | 283 | 282 |
| Claude | 390 | 304 | 304 |
| ChatGPT | 347 | 272 | 272 |
| WeChat | 95 | 22 | 22 |

这组数据同时保留本地更慢和更快的情况。GitHub 两次均新建连接，其余目标这两次大部分复用了连接。未通过调整倍率、减去固定常数或隐藏失败来制造一致结果。

## 落地调整

- 默认分组改为与官网本次列表一致的七站；AI 十五站仍可选择。
- 保留单次和每站十次最低值两个明确模式，没有暗中预热或丢弃首测。
- 增加“本次采样明细”：实际目标 URL、首测、最低成功值、已完成次数、逐次状态与时间；复制报告也保留时间。
- 没有分段计时权限时，界面保持 DNS / TLS 未知，不把首测自动标成冷连接，不把小数值自动标成复用连接。跨域细节的限制见 [Resource Timing](https://www.w3.org/TR/resource-timing/)。
- 保留原工作台外观及 `/#connectivity` 入口。

## 验证与证据

类型检查、构建、调度回归通过。新增断言确认首测 620 ms 与最低成功值 75 ms 分别保留，各次采样都有时间戳，默认分组为七站。

真实 Chrome 界面另完成七站各十次、共 70 次采样：七张明细卡均显示 10 / 10。Google 首次未获响应，后续最低 248 ms；ChatGPT 首次 1086 ms，后续最低 274 ms。首测失败及后续全部结果均保留。这组只验证采样记录与展示，不具有对应的完整 Network 分段，不用它判断连接是否复用。截图位于 `docs/connectivity-check/parity-audit-ten.jpg` 和 `parity-audit-details.jpg`。

最后重新加载到默认七站单次模式，得到三站响应、四站未获响应。四个请求的 Chrome 终止事件为 `net::ERR_ABORTED`，发生在发起后 3603–3612 ms，未返回具体 blockedReason；这与应用 3600 ms 超时终止一致，只证明期限内没有获得响应，无法定位期限内阻塞在 DNS、代理、连接、TLS 或站点处理的哪一步。没有通过再次重跑替换掉本次失败。结果保存在 `chrome-final-single.json`、`chrome-final-aborts.json`，最终页面截图为 `docs/connectivity-check/parity-final-single.jpg`。

原始记录位于本地忽略目录 `artifacts/connectivity-parity/`：`chrome-initial.json` 保留最初失败；`chrome-local-repeat.json` 保留新连接分段；`paired-chrome.json` 为上述完整交替对照。文件仅保存公共目标、必要请求参数和计时，没有保存 Cookie、认证头或页面 IP 信息。
